# Branch Hygiene

This skill sweeps local branches and worktrees whose work has landed, under Safe Set and Hard Rules, and leaves everything else alone. A finished plan's worktree is cleared by step 10 of `finishing-work`. This skill reaps a tree that step left, and each merged branch, only where Safe Set admits it.

The SessionStart nudge flags **reapable** branches, merged and safe to sweep, and **stranded** ones, whose remote is gone because the PR merged while the branch holds commits that never reached the trunk. Stranded branches take priority: recover them before sweeping anything.

## Safe Set

A local branch is auto-reaped only if it is **verified merged into the integration branch**. For a branch with an open or merged pull request, the integration branch is that pull request's base as the host reports it, read at the act. On GitHub the read is `gh pr view <branch> --json state,baseRefName`, and the ref the procedures use is `origin/<baseRefName>`, after a fetch. Its base counts only where its state is OPEN or MERGED. Where it prints CLOSED or MERGED, `gh pr list --head <branch> --state all --json number,state,mergedAt,baseRefName` lists them, and the open one's base governs, else the most recently merged one's. On a GitHub remote, a read that fails for any reason but `no pull requests found` is a stop, not a fallback. A local branch whose name is all digits, after an optional leading `#` and then an optional `+`, is reported and left unreaped, and no `gh pr view` is run on it, since `gh` reads such a word as a pull request number. For a branch with no open or merged pull request, a remote with no such read, or a merged pull request whose base is gone after the fetch or already an ancestor of the fallback (`git merge-base --is-ancestor origin/<baseRefName> <fallback>`), the integration branch is `origin/develop` if it exists, else `origin/main`, else `origin/master`. A merged pull request also takes that fallback where its base had already landed when it merged. A protected base never does: `develop`, `main`, `master` or the repo's default branch, which `gh repo view --json defaultBranchRef` names. Any other base had already landed where the governing pull request's `mergedAt` is later than every `mergedAt` that `gh pr list --head <baseRefName> --state all --json number,state,mergedAt` prints for the base's own merged pull requests. The governing pull request's `mergedAt` comes from the list row that governs. Where the base's list holds no merged pull request, the base governs. The session-start nudge resolves only that fallback, so a branch it flags as stranded is re-read against its pull request base before any recovery.

The sweep below tests every branch against that fallback, by ancestry, since one ref serves every branch and a branch whose work reached the trunk has landed whatever its base. A stacked branch whose work sits only in its parent is reaped once the parent lands. The ancestry test reads a merge-commit merge as landed, while a squash or rebase merge leaves a landed branch reading unmerged, which keeps it. A worktree is reaped only if it lives under `.claude/worktrees/`, sits on a reapable branch, and has a clean working tree. A detached worktree nested in a reapable one takes the branch test as `git merge-base --is-ancestor HEAD <integration-ref>`, run inside it.

Protected, never touched: `develop`, `main`, `master`, the current branch, the repo's default branch, and a worktree outside `.claude/worktrees/`.

## Procedure

1. `git fetch --prune` to refresh the integration and remote-tracking refs. If it fails or no integration ref resolves, stop and report without deleting.
2. Resolve the integration ref for the sweep, the fallback under Safe Set.
3. Compute the merged set: `git branch --merged <integration-ref>`, minus the protected list.
4. For each merged branch, read its tip once, `<sha>`, with `git rev-parse --verify refs/heads/<name>`, and confirm `git merge-base --is-ancestor <sha> <integration-ref>` exits 0, either read failing leaving the branch reported. If the safe set admits its worktree, remove it under the rules below. Then, where `git worktree list --porcelain` exits 0 and prints no line equal to `branch refs/heads/<name>`, run `git update-ref -d refs/heads/<name> <sha> --no-deref`, which refuses where the tip moved since the read and never follows a symbolic ref to the branch it names. Where the delete exits 0, run `git config --remove-section branch.<name>`, which removes the branch's `remote`, `merge` and `pushRemote` settings that `update-ref` leaves standing, so a later branch cut under the same name inherits no upstream nobody chose for it. It exits 128 where the branch had no section, and that exit is no report. Any other non-zero exit is a report naming the branch, whose section stays. A refusal, a listing that fails or a line naming the branch is a report, not a delete. Every branch-name operand in this skill's commands, the integration ref's included, is written as a single-quoted literal. Git admits `$`, a backtick and `;` in a branch name, and a shell expands an unquoted name before git reads it. A name holding a quote character, a typographic single quote from U+2018 to U+201B among them, is a report, not a delete.
   - Read the machine's registry, and any roster, for each live session but the seat's own whose `Repo:` names the worktree's repository. A seat whose next pass reads a record of its own tells each live session that has not cleared, once, and keeps each notice and clear there, so a clear holds across later sweeps. A seat with no such record tells no one and removes no tree while any session it read above is live. A session counts as live unless its entry reads as exited, so one whose heartbeat reads unknown counts as live, and a registry or roster read that fails or reads in part leaves the tree. Leave the tree and its branch in place for step 5 while any live session has not cleared. Never `git switch` a checkout the seat does not own.
   - Take worktrees deepest path first. A nested worktree the safe set admits goes before its parent, any child left in place leaves its parent in place, and a parent left in place admits no child. `git worktree prune` runs only where every prunable entry in the checkout sits under the reaped worktree.
   - Before `git worktree remove`, list its reparse points with `cmd //c 'dir /AL /S <path>'`, the path in Windows form and "File Not Found" an empty listing, each link's path the `Directory of` path joined to the text between its tag and any ` [<target>]`, or `find <path> -type l` off Windows. Take the shallowest listed link and remove it only where `git -C <path> ls-files --error-unmatch <link>` exits 1, as a link, never recursively: `cmd //c 'rmdir <link>'` for a link tagged `<JUNCTION>` or `<SYMLINKD>`, `cmd //c 'del <link>'` only for one tagged `<SYMLINK>`, `rm <link>` elsewhere. A link tagged none of the three is left, with its worktree. List again until empty. Any other exit, a listing that errors, a link that will not go, or an unlinking that dirties the tree leaves the worktree in place. The worktree path and each link name are written as single-quoted literals in `find`, `git -C` and `rm`, and the `cmd` string is single-quoted whole, since Git Bash expands `$` and a backtick inside a double-quoted one and hands a double quote inside it to `cmd` as `\"`. A link's name is the tree's own contents, so whoever wrote the tree chose it. A path or link name holding a space, a tab, a comma, a semicolon or an equals sign is a report, since `cmd` splits an argument at each. So is one holding a quote character of either kind, or any of `&`, `|`, `<`, `>`, `^` and `%`, which `cmd` reads as its own whatever quotes the string. So is a `find` listing holding a line that does not open with the worktree path followed by `/`, since a link name holding a newline prints as two lines and `rm` takes the second from wherever the command runs. The link and its worktree are left.
5. Report in two parts:
   - **Reaped:** each branch and worktree removed, with `restore: git branch <name> <sha>`.
   - **Left for you, with the reason:** a branch with its upstream gone but unmerged; a branch ahead of the integration ref whose PR merged, likely stranded (see Stranded Branch Recovery); any other unmerged branch; any dirty worktree; any reapable-looking worktree outside `.claude/worktrees/`; a local branch the Safe Set read reported for a name `gh` would read as a pull request number. Also any worktree, with its branch, step 4 leaves in place for a live session, nested worktree or reparse point, and a merged branch checked out in a checkout the seat does not own, reported here and to that checkout's live session. List them and delete none.

## Stranded Branch Recovery

Recover a stranded branch's commits before deleting it. Here the integration ref is the stranded branch's own, per Safe Set:

1. Confirm the stranded commits: `git log --oneline <integration-ref>..<branch>`.
2. Branch fresh from the current integration ref: `git switch -c <branch>-recover <integration-ref>`. Never reuse the merged branch, which is frozen.
3. Bring the commits over: `git cherry-pick <integration-ref>..<branch>`.
4. Push the recovery branch and open a new PR against the integration branch.
5. Delete the stranded original only under the exception in "The only auto-delete trigger".

## Hard Rules

- The only auto-delete trigger is membership in `git branch --merged <integration-ref>`. Never delete a branch outside that set, with one licensed exception: a stranded original once `git rev-parse --verify origin/<recovery>` prints the same hash as `git rev-parse <recovery>` and `git cherry <recovery> <stranded>` prints no `+` line. One condition missing is a report, not a delete. Every delete, the exception's included, is `git update-ref -d refs/heads/<name> <sha> --no-deref` on a tip read once before the condition that licenses it, after `git worktree list --porcelain` exits 0 and prints no line equal to `branch refs/heads/<name>`, since `update-ref` has no refusal of a checked-out branch. Each delete that exits 0 is followed by step 4's `git config --remove-section branch.<name>`, the exception's included. A moved tip, a failed listing or a named checkout is a report, not a delete. "Upstream gone" alone is a report, not a delete.
- Never `git worktree remove --force`. A dirty worktree is reported, never removed.
- Never touch anything on the protected list under Safe Set.
- Never reach a tag. The fetch carries no `--prune-tags`, and a delete under `refs/heads/` reaches a branch and never a tag, so a `rollout/*` deploy mark survives the reaping of the branch it marks. A git config setting `fetch.pruneTags` or `remote.<name>.pruneTags` makes every `--prune` fetch prune tags too, the reaper's included, so a repository holding deploy marks leaves both unset.
