# Test Gates

Lane commands are per-repo facts, recorded in that project's memory tier when a repo first defines its lanes and read from there. Nothing in this file is a command to run. Which tests a change earns and keeps lives in `skills/testing-discipline/SKILL.md` under the kit plugin root.

## Layer Map

**A repository's tests are mapped by what they cost to run, and the map is a per-repo fact beside the lane commands.** It is held as `layers` in the repo's committed lane map where it has one, and as a project memory otherwise. Every repo names its layers differently, so the map records the repo's own names against one ladder: in-process tests with no external resource, tests against a database, tests against a process or a port, tests driving a whole flow end to end. Each rung records its test count and its measured clock, read from a real run with the moment-pin below. A rung with no measured clock reads `cost: unmeasured`. The map is what the architect reads when allocating a section's tests by layer, and it sizes no lane. A repo wants many tests on the first rung and few on the last, and the map is how a session sees which rung a candidate joins before writing it.

## Test Lanes

The doctrine's gate bullet ("After each step, run the lane the moment calls for, and report the delta") names which moment takes which lane.

- **The targeted lane** is the changed files' tests plus any whole-tree pin whose subject those files are. A change to a family member runs the family's pin whatever file it sits in.
- **The whole gate** is the full suite. The finishing gate runs at finishing, before the plan's handoff, on the lane the lane script prints from the repository's lane map, `test/gate-lanes.json` in the kit. The script is `scripts/gate-lane.js` under the kit plugin root. It prints `lane: whole` where the map cannot bound the delta or the daily gate below has no fresh green run, and its header lists each case. Finishing and the handoff are one moment. A plan pays one green finishing run, and every change after it takes the targeted lane over its own delta. The one finishing gate is the run that ends green, so a red of the plan's own is fixed and the gate re-run on a fresh lane-script report. A red the integration branch's head carries too is the trunk's, and the base-head bullet below routes its fix. A gate whose only reds are the trunk's is the one paid once each of them is fixed or has become a spec. A merge takes the whole gate only where a code file conflicted or both sides changed one. Any other merge takes the targeted lane over the files either side changed. Each side's changed files are those `git diff --name-only <merge-base> <side>` lists, and both sides changed a code file only where the same one appears on both lists. A code file is one that runs or is loaded by what runs. That covers a source file, a script, a hook, a test file, a query or schema file, and a config file a hook, script or program reads to decide what it does, a settings file or a plugin manifest among them. Three kinds are not code files for this rule: markdown, a skill's `SKILL.md` and a probe included; plain text; and a budget or fixture file that only tests and the tool maintaining it read, as `test/size-budget.json` is. The targeted lane of each of those runs the tests that read it. A merge whose diff touches the sources a local build artifact is stamped from rebuilds before it gates. The merge leaves the stamp stale with no conflict to flag it. In the kit repository those sources are the files under `plugins/grimoire/hooks/`, rebuilt with `build.ps1` or `build.sh`.
- **The contention lane** holds the tests whose subject is genuinely machine-shared state (a machine-global tier, a real shared lock), each saying so in its own text. It runs serially, beside the finishing gate or any whole gate, and at section close whenever that section's delta touched the lane's subject. A main-gate test that needs the box to itself moves here, which is the fix, rather than the main gate being retried until it passes.
- **The whole gate's baseline is the base head.** No plan runs the whole gate at its start to record a baseline. The finishing gate runs once, after the plan's branch has taken in the integration branch. Where the gate reds any test file, add one worktree under the project's `.kit/` scratch path at the integration branch's commit that merge took in, built first where the project's tests read a build output. Where no merge took the integration branch in, as under Review-Only or Commit-and-Push on the trunk, the worktree sits at the effort's base ref, which finishing-work's base-ref paragraph derives. Run each red file there alone with the project's own test command, then remove the worktree. The re-run takes its own worktree because a whole gate reads the tree live, and the finishing pass is still editing the plan's tree. Each base-head result rides the Chapter's `Gate:` line beside the gate's own counts, as `base head <sha>: <file> <pass>/<fail>`. A file red on the branch alone is the plan's, fixed on the plan's branch. So is a file the base head does not hold, which rides the line as `absent` in place of its counts. A file red on both sides is the trunk's. The red protocol below still names it flake or regression, and then the session fixes it before the handoff, on a branch cut from the trunk with a pull request of its own. That fix takes the targeted lane over the failing file, and the plan's branch merges the trunk again once it lands. That merge takes the targeted lane over the files the fix changed, even where the plan changed one of them too, and any other file it brings across takes the merge rule the whole-gate bullet above states. A red whose fix is a design of its own becomes a spec instead. The handoff waits on that pull request or that spec. A trunk red never goes to the kaizen inbox or the backlog, since a red left for later stays red for every plan after this one. A defect that reached the trunk or a live run past a green gate is recorded in the repository's escaped-defect set by the plan that fixes it, founding the set where the repository has none, as an entry where an offline check now sees it and otherwise with the reason none can.
- **The daily gate is the trunk's whole gate once a day, slow suites admitted, skipped where the day's diff holds no code file.** A red narrowed to one trunk commit takes the base-head bullet's trunk-red route that day. A commit with no fix draft by the next run is reverted by an architect plan, its work returning under a new plan.
- **The audit lane is the mutation run below.** It runs under a prune plan over one folder at a time, or over one section's delta when a reviewer flags it, and never as a gate.

## Reading a Red

A red is discriminated by protocol, not by re-running the world:

1. **Capture the exit code and the discriminating output from the run itself**: a foreground run's own exit status, or a backgrounded run's marker and the error text in its own log. Where the environment refuses the marker compound, read the run's own summary output after the notification instead.
2. **Solo, then class, then a full re-run with no code change, then a clean tree.** Solo separates the test from its neighbors. The class run separates the fixture from the box. The unchanged full re-run separates the code from the machine. The same red at the base head the base-head bullet above defines separates a red that was there before you from one you caused.
3. **Name it flake or regression, with the reason, before moving on.** The reason cites the discriminating output from step 1, never the timing or the feel of the failure.

A red seen with another suite, build or embedding pass on the box that passes on a solo re-run is contention evidence. It goes to the kaizen inbox as a note stating which suite cannot share the box with what, whatever repository the suite belongs to.

## Clock and Box

- **Capture the clock with the baseline.** Record the suite's wall clock beside the baseline's pass/fail counts, and name the lane the baseline ran on. The whole gate's clock is read against the daily gate's last run on the same machine, else the last `lane: whole` finishing Chapter under `docs/archive/`, else the last one with no verdict line. Growth past a few minutes, net of skipped slow suites, is a finding under the contention rule below.
- **The gate line names the slowest files and the fixture time.** Beside the clock, the Chapter's `Gate:` line carries the five slowest test files by summed test time and the time spent in fixtures before any test ran, each with its figure. A runner's per-test log charges fixture setup to no test, so a suite whose summed test time falls short of its wall clock is spending the difference in fixtures, and that cost is measured by a timer in the fixture base class or not at all. Growth in a file's figure is a finding against the section that touched it. A test that reaches a full environment belongs on the daily gate's rung, not the finishing gate's.
- **The gate line carries the section's test ledger.** Tests added, tests retired, and test lines over production lines for the section's delta, counting only code files as the whole-gate bullet defines them. The figures are reported for the reviewer to read against the section's `Tests:` allocation and are enforced by nothing, since a ratio a hook blocks on is gamed within a week.
- **Moment-pin a measured figure.** A measured figure recorded in a journal-layer artifact carries a moment-pin: what produced it, when, on which machine, and under what contention. The machine is part of the pin, since the configuration epoch a figure is read against is recorded per hostname, and the memory-system skill owns that record and the expiry rule that reads a figure against it. Within a plan doc, pinned figures sit only in its Chapters, its interim board entries and its Evidence section. Deep evidence behind a figure, such as a scatter analysis, lives in memory or in that Evidence section, and a journal line cites it there.
- **Record the contention beside the clock.** Every wall-clock figure carries the box's process count and free memory, captured at the run. Growth is a finding only against a baseline at comparable contention or a same-conditions trend.
- **Check the box before any suite.** Poll as the doctrine's machine-budget bullet ("One heavy process at a time is a per-machine budget, not a per-directory one") states, counting a runner or build whatever its engine, whether owned by another session or by a running engine. The poll is a sample, never a clearance. It cannot see in-process agent fan-out, which spawns no engine, and it cannot see a neighbor that starts after the sample and before the suite. A clean poll is a basis for starting and never proof the box is empty. A machine-state sentence leaving the session names the poll and its age, or says "not polled this turn".

## Mutation Audit

**A mutation run measures what a test detects, and it is the only instrument that does.** The tool introduces one small deliberate defect into the production code at a time, a flipped comparison, a dropped statement, a constant in place of a return, and runs the tests that cover the line. A test that fails killed the mutant. A mutant no test fails on survived. The score is the share killed, and the score is not the useful part. The per-test kill sets are, since two of testing-discipline's retire symptoms fall out of them mechanically: a test that stays green while the behavior it pins breaks has an empty kill set, and a test whose defects are caught elsewhere has a kill set another test's contains.

**The run credits every failing test, or its per-test data is wrong in a known direction.** A tool's default stops a mutant's run at the first failures, so a test scheduled later is never credited and looks useless. Stryker's `disable-bail` and its equivalents in other tools are on for every audit, and a kill set from a run without it is not read. The score is unaffected either way.

**The run is scoped, because its cost is the mutant count times the covering tests' clock.** A folder of a few thousand production lines takes a quarter hour on a small box with fast tests, and a folder whose tests build a database takes hours. The audit runs over one folder under a prune plan, or over one section's changed lines with the tests that section added when a reviewer flags it, with the tool's incremental mode where it has one. The run's clock and box ride the moment-pin like any figure. A tool run is bounded by the tool's own per-mutant timeout, and a hand-rolled mutation run takes testing-discipline's hang-limit rule.

**The audit produces three lists, and each list is a question, never a verdict.**

- A test that kills no mutant asks whether the defect it names is one the mutator can produce. A record's shape, an enum's membership and a pure function's refusal to mutate its input yield no mutant, and a test of one stands or falls on testing-discipline's two triage questions alone. A test that kills nothing where the mutator reaches is opened and read.
- A test whose kill set another test's contains asks whether it pins a contract the other does not name, and whether its red localizes a defect the other's red only reports. Testing-discipline's duplicate class rules it.
- A survivor on a line a section changed asks whether the section's tests check the behavior they are named for. A test named for a rule whose boundary comparison survives under its coverage has an assertion too loose to see the rule, and the repair is to strengthen it, not retire it.

A family of tests on one fixture with identical kill sets is read under testing-discipline's shared-setup rule.

**A prune plan runs the audit before the doctrine lands, or the suite keeps teaching the old pattern.** A session copies the shape it sees in the files it joins, so the retire pass over the existing suite is what makes the authoring rules take.
